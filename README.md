# ЛКЛАУД — плагін розкладу та профілю

Плагін підключається до віддаленого MCP `https://dev.nns.in.ua/mcp` через OAuth із автоматичною реєстрацією клієнта (DCR). MCP, вибір хмари, вхід і згоду реалізує компонент `users` WebNNS. Компонент `cloud` не використовується.

Пакет узгоджено з [WebNNS b7a3cc3](https://github.com/NStadnik/WebNNS/commit/b7a3cc3e73c1a21524e66dc95489b714cae99db7). Контракт сервера та налаштування: [OAuth і MCP у users](https://github.com/NStadnik/WebNNS/blob/b7a3cc3e73c1a21524e66dc95489b714cae99db7/docs/lklaud-oauth-gateway.md).

## Встановлення та авторизація

1. Додати маркетплейс із джерелом `https://github.com/NStadnik/lcloud_ai_plugin`.
2. Встановити ЛКЛАУД версії **0.2.0** або новішої й запустити підключення/авторизацію у клієнті.
3. На сторінці OAuth вказати адресу власної хмари закладу.
4. Після перенаправлення увійти на сайті закладу й підтвердити доступ до розкладу та, за потреби, профілю.
5. Повернутися до клієнта. Для перевірки попросити показати доступні можливості або власний розклад.

**Поле адреси хмари показує сторінка OAuth у `users`, а не картка маркетплейсу.** У версії 0.1.0 головний manifest запускав локальний stdio без цього сценарію. Після оновлення джерела на GitHub синхронізуйте маркетплейс, оновіть або перевстановіть плагін і пройдіть авторизацію заново. Не редагуйте кеш встановленого плагіна.

Клієнт виконує DCR автоматично. Пароль вводиться лише на сайті закладу; токени та секрети в чат або пакет плагіна не передаються. Node.js, `npm run configure` і ручне створення персонального токена для основного плагіна не потрібні. Майстер першого підключення оголошено через `onboardingSkill` у `plugin.json`.

Центральний режим підтримує активні хмари зі спільною головною БД платформи та записами в `domen`. Зовнішні інсталяції з іншою головною БД потребують окремого налаштування довіри; довільна адреса не гарантує підключення.

## Підготовка WebNNS адміністратором

1. Застосувати оновлення `users` у головній БД та хмарах, оновлення `preference` і потрібні права. Розгорнути класи, хелпери та `.htaccess` однієї версії.
2. У `/preference/edit` головної хмари ввімкнути «Єдиний публічний плагін ЛКЛАУД», указати центральний origin `https://dev.nns.in.ua` без `/mcp`, зберегти, потім увімкнути OAuth платформи.
3. Перевірити права `users.mcp`, `users.api`, `users.oauth_discovery`, `users.oauth_gateway_*`, `users.oauth_local_authorize`, `users.oauth_federation_authorize` і `users.oauth_federation_api` за інструкцією WebNNS. Для керування налаштуваннями потрібне `preference.oauth_settings`. Окреме право `rozklad.api_personal` у новому контракті не створюється.
4. Перевірити, що домени закладів активні в головній БД, а облікові записи мають потрібні профілі, права й доступ до компонентів.

Конфігурація OAuth зберігається у БД: `users_oauth_platform_settings`, `users_oauth_clients`, `users_oauth_hub_settings`, `users_oauth_hub_cloud` у головній БД; локальне ввімкнення та ключ — у `users_oauth_settings` кожної хмари. `users` створює окремі ключі автоматично. Не копіюйте ключі між хмарами.

`single.json` і властивості `LKLAUD_OAUTH_*_CONFIG_FILE` більше не читаються WebNNS. Старий `scripts/provision-oauth.mjs` завершується поясненням міграції та не створює файлів. Якщо раніше використовували файлову конфігурацію, **до першого запуску нової версії** перенесіть незмінний локальний ключ та клієнтів у БД за інструкцією WebNNS.

Основний MCP виконується в PHP `users`; окремий Node HTTP-процес не потрібний. Центральний OAuth discovery має оголошувати `registration_endpoint`, `S256` і `token_endpoint_auth_methods_supported: ["none"]`. DCR сервера допускає точні callback URL ChatGPT; сумісність callback конкретного Codex-клієнта потрібно перевірити окремо.

## Інструменти

| Інструмент | Призначення |
| --- | --- |
| `get_available_capabilities` | Можливості підключеного облікового запису |
| `get_my_profile` | Власний профіль за дозволом `profile:read` |
| `get_my_schedule` | Власний розклад за дозволом `schedule:read` |

Доступні інструменти визначаються capabilities, правами й scopes на сервері. Відсутність дозволу на профіль не повинна блокувати читання дозволеного розкладу. Плагін не приймає від моделі довільні ID користувача, викладача, групи чи адресу іншої хмари для виклику інструментів.

Приклади: «Покажи мій розклад на сьогодні», «Які можливості доступні в моїй хмарі?», «До якого облікового запису я підключений?».

Для розкладу дозволені лише `date_from` та `date_to` у форматі `YYYY-MM-DD`, включно з межами, максимум 31 календарний день. Враховуйте `timezone`, не вигадуйте відсутній час, за `truncated=true` звузьте період. Порожній `items` означає відсутність занять; помилка сервера — потребу усунути помилку.

## Діагностика

| Ситуація | Дія |
| --- | --- |
| Немає поля адреси | Запустити OAuth-підключення; поле показує сторінка `users` центральної хмари |
| Клієнт запускає локальний Node | Оновити маркетплейс і перевстановити плагін 0.2.0 або новіший |
| `oauth_disabled` | Перевірити спільне й локальне ввімкнення OAuth |
| `oauth_not_configured` | Перевірити центральний режим і налаштування OAuth у `preference` |
| `oauth_schema_required` | Застосувати оновлення БД `users` |
| Невідомий заклад | Перевірити активний запис домену у спільній головній БД |
| Токен відкликаний або прострочений | Повторити OAuth-підключення |
| `invalid_redirect_uri` при DCR | Перевірити callback клієнта та дозволені сервером точні URL |

GET `/mcp` повертає 405 за контрактом stateless Streamable HTTP. Це не перевірка авторизації: MCP-запити виконуються через POST; без Bearer-токена сервер має повернути 401 з `WWW-Authenticate` і посиланням на resource metadata.

## Розробка та попередні локальні режими

Для перевірок потрібні Node.js **22.16+** та npm:

```sh
npm ci
npm run check
npm test
```

Перевіряються manifest-файли, OAuth DCR, onboarding skill, YAML, версії, синтаксис і попередні локальні API-адаптери. Модульні тести використовують змодельовані відповіді; вони не замінюють реальний OAuth-вхід у клієнті.

`server/index.mjs`, `scripts/configure.mjs` та `server/http.mjs` збережені для попередніх локальних інтеграцій і не запускаються головним `mcp.json`. За явного вибору старого stdio користувач виконує `npm run configure` у терміналі, уводить адресу хмари й персональний токен `/user/api_access`. Дані зберігаються в `~/.config/lklaud/connection.json` із правами `0600`; вони не використовуються віддаленим OAuth-плагіном. Пара `LKLAUD_CLOUD_URL` і `LKLAUD_API_TOKEN` або `LKLAUD_CONFIG_FILE` застосовується лише до цього локального режиму. Сервер не читає `.env` автоматично.

Для окремого попереднього Node HTTP-адаптера залишаються `LKLAUD_CLOUD_URL`, `LKLAUD_MCP_RESOURCE`, `LKLAUD_MCP_PORT` і `npm run start:http`. Він підтримує одну хмару та не реалізує новий центральний вибір закладу. Для центрального режиму використовуйте PHP `/mcp` WebNNS.
