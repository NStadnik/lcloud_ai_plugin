# ЛКЛАУД — плагін розкладу та профілю

Плагін підключається до віддаленого MCP вибраного сервера через OAuth із автоматичною реєстрацією клієнта (DCR). MCP, вибір хмари, вхід і згоду реалізує компонент `users` WebNNS. Компонент `cloud` не використовується.

| Середовище | Адреса сервера | MCP endpoint |
| --- | --- | --- |
| Основне | `https://lcloud.in.ua` | `https://lcloud.in.ua/mcp` |
| Тестове | `https://dev.nns.in.ua` | `https://dev.nns.in.ua/mcp` |

**Адресу сервера користувач має вказувати під час встановлення плагіна, до початку OAuth.** `dev.nns.in.ua` призначений для тестування. Для звичайної роботи використовується `lcloud.in.ua`. Вибрана адреса визначає MCP endpoint і OAuth discovery для цього підключення.

У версії **0.3.0** адресу вводять у браузерному майстрі налаштування. Фіксоване підключення до тестового сервера прибрано з `mcp.json`. Майстер працює локально на комп’ютері користувача та налаштовує віддалений MCP через штатний Codex CLI.

## Встановлення та авторизація

Потрібні Node.js **22.16+** і Codex CLI або встановлена програма ChatGPT із bundled CLI. Залежності npm для майстра не потрібні.

1. Додати маркетплейс із джерелом `https://github.com/NStadnik/lcloud_ai_plugin` і встановити ЛКЛАУД **0.3.0** або новіший.
2. Натиснути **«Налаштувати»**. Клієнт запускає навичку `lklaud:setup`, яка відкриває браузерний майстер. Цей короткий запуск у чаті є механізмом onboarding клієнта; адресу вводять у формі браузера.
3. У єдиному полі **«Введіть адресу хмари (ЛКЛАУД чи Бухлік)»** ввести адресу своєї хмари без шляху. Адреса має використовувати HTTPS; якщо ввести лише домен, `https://` додається автоматично. Суфікс `/mcp` додається автоматично.
4. Натиснути **«Продовжити до авторизації»**. Майстер перевіряє MCP/OAuth discovery вибраного сервера. Після успішної перевірки Codex записує URL підключення й відкриває OAuth-вхід.
5. На сторінці OAuth вказати адресу власної хмари закладу, якщо сервер запитує її для центрального режиму. Увійти на сайті закладу та підтвердити потрібні дозволи.
6. Після повідомлення про успішне підключення повернутися до клієнта, оновити список MCP-серверів або відкрити новий чат. Для перевірки попросити власний розклад.

Для ручного запуску того самого майстра з папки плагіна:

```sh
npm run setup
```

`node scripts/setup.mjs --no-open` запускає форму й виводить її локальну адресу без автоматичного відкриття браузера. Це використовується навичкою setup разом із браузерним інструментом. Майстер діє 15 хвилин; повторний запуск дозволяє змінити сервер або повторити авторизацію.

Адреса сервера підключення та адреса хмари закладу в центральному режимі — два окремі налаштування. Сервер вибирається у формі **до OAuth**, хмару закладу може додатково запитати сторінка `users`.

Підключення зберігається в користувацькій конфігурації Codex як **`lklaud-user`** через `codex mcp add lklaud-user --url ВИБРАНИЙ_ORIGIN/mcp --oauth-client-registration dcr`. Ця команда запускає штатний OAuth-потік; паролі та токени обробляє Codex. Зміна адреси замінює попередній запис `lklaud-user`; інші MCP-підключення не змінюються. Невдала перевірка discovery не змінює конфігурацію. Якщо помилка сталася вже під час OAuth, URL може бути збережено, але вхід ще не завершений. Повторити вхід можна командою `codex mcp login lklaud-user`.

Після видалення пакета плагіна окреме користувацьке MCP-підключення залишається в Codex. За потреби видаліть його через налаштування MCP або `codex mcp remove lklaud-user`. Не редагуйте manifest у кеші плагіна.

Майстер не зберігає паролів і OAuth-токенів, не передає їх у чат та приймає форму лише на локальному loopback із перевіркою Host, Origin і CSRF. Компонент `cloud` не використовується. Поточний Codex не підтримує форму довільного URL всередині статичного bundled MCP; тому вибір реалізовано через onboarding і штатне користувацьке MCP-підключення.

Центральний режим підтримує активні хмари зі спільною головною БД платформи та записами в `domen`. Зовнішні інсталяції з іншою головною БД потребують окремого налаштування довіри; довільна адреса не гарантує підключення.

## Інструменти

| Інструмент | Призначення |
| --- | --- |
| `get_available_capabilities` | Можливості підключеного облікового запису |
| `get_my_profile` | Власний профіль за дозволом `profile:read` |
| `get_my_schedule` | Власний розклад за дозволом `schedule:read` |

Доступні інструменти визначаються capabilities, правами й scopes на сервері. Відсутність дозволу на профіль не повинна блокувати читання дозволеного розкладу. Плагін не приймає від моделі довільні ID користувача, викладача, групи чи адресу іншої хмари для виклику інструментів.

Приклади: «Покажи мій розклад на сьогодні», «Які можливості доступні в моїй хмарі?», «До якого облікового запису я підключений?».

Для розкладу дозволені лише `date_from` та `date_to` у форматі `YYYY-MM-DD`, включно з межами, максимум 31 календарний день. Враховуйте `timezone`, не вигадуйте відсутній час, за `truncated=true` звузьте період. Порожній `items` означає відсутність занять; помилка сервера — потребу усунути помилку.

## Діагностика

| Ситуація | Дія |
| --- | --- |
| Після «Налаштувати» відкривається чат із `lklaud:setup` | У 0.3.0 навичка має одразу запустити браузерний майстер. Якщо вона лише перевіряє capabilities, установлено старий setup: синхронізуйте маркетплейс і перевстановіть плагін |
| Немає форми вибору адреси | Запустити «Налаштувати» або `npm run setup`; адреса вибирається у браузерному майстрі |
| Центральний сервер запитує адресу закладу | Указати адресу власної хмари на сторінці OAuth `users` |
| Після успішного входу немає інструментів | Оновити список MCP-серверів або відкрити новий чат; перевірити наявність `lklaud-user` |
| `oauth_disabled` | Перевірити спільне й локальне ввімкнення OAuth |
| `oauth_not_configured` | Перевірити центральний режим і налаштування OAuth у `preference` |
| `oauth_schema_required` | Застосувати оновлення БД `users` |
| Невідомий заклад | Перевірити активний запис домену у спільній головній БД |
| Токен відкликаний або прострочений | Повторити OAuth-підключення |
| `invalid_redirect_uri` при DCR | Перевірити callback клієнта та дозволені сервером точні URL |

GET `/mcp` повертає 405 за контрактом stateless Streamable HTTP. Це не перевірка авторизації: MCP-запити виконуються через POST; без Bearer-токена сервер має повернути 401 з `WWW-Authenticate` і посиланням на resource metadata.

## Розробка та попередні локальні режими

Для перевірок потрібні Node.js **22.16+** та npm:

```sh
npm ci
npm run check
npm test
# Якщо встановлений Codex CLI:
npm run check:host
```

Перевіряються manifest-файли, браузерна форма, введення адрес основної, тестової та власної хмари, нормалізація URL, OAuth discovery, захист локальної форми, аргументи CLI, YAML, версії, синтаксис і попередні локальні API-адаптери. Додаткова `check:host` викликає справжній парсер установленого Codex через `plugin/read` на тимчасовому пакеті та перевіряє setup skill і відсутність фіксованого MCP. Вона не встановлює плагін і не запускає OAuth. Модульні тести використовують змодельовані відповіді; вони не замінюють реальний OAuth-вхід у клієнті.

`server/index.mjs`, `scripts/configure.mjs` та `server/http.mjs` збережені для попередніх локальних інтеграцій і не запускаються головним `mcp.json`. За явного вибору старого stdio користувач виконує `npm run configure` у терміналі, уводить адресу хмари й персональний токен `/user/api_access`. Дані зберігаються в `~/.config/lklaud/connection.json` із правами `0600`; вони не використовуються віддаленим OAuth-плагіном. Пара `LKLAUD_CLOUD_URL` і `LKLAUD_API_TOKEN` або `LKLAUD_CONFIG_FILE` застосовується лише до цього локального режиму. Сервер не читає `.env` автоматично.

Для окремого попереднього Node HTTP-адаптера залишаються `LKLAUD_CLOUD_URL`, `LKLAUD_MCP_RESOURCE`, `LKLAUD_MCP_PORT` і `npm run start:http`. Він підтримує одну хмару та не реалізує новий центральний вибір закладу. Для центрального режиму використовуйте PHP `/mcp` WebNNS.
